# Lossless PNG feasibility

## Execution prompt

Continue the ordered backlog from updated develop with one bounded research task:
benchmark browser-local PNG encoders before implementing Lossless PNG Optimizer.
Read AGENTS.md and the development, communication, SDLC and applicable engineering
skills. Inspect the existing PNG compressor and upstream issues #359/#295 and PR #461.
Compare the installed palette compressor at maximum quality, native canvas PNG
and native IDAT recompression without decoding/re-encoding samples. Use generated
fixtures, including gradients with more than 4096 colors, alpha/hidden RGB,
metadata, 16-bit, indexed and interlaced PNG. Independently check decoded pixels,
raw filtered samples, dimensions, non-IDAT metadata and non-inflation selection.
Record reproducible per-browser bytes/timings, limits, dependency/license tradeoffs
and an explicit proceed/defer decision. Do not add a runtime feature, WASM/package,
upload, persistence or production deployment. Keep experimental code outside src.
Review and validate, deliver one PR into develop with exact-head required CI and
verified cleanup. Do not start implementation of the next slice automatically.

## Question and scope

Can the current dependency or a dependency-free browser encoder meet a strictly
lossless sample/metadata contract, and is the saving useful enough to justify a
separate worker/UI implementation? This spike measures synthetic fixtures, not
representative customer compression ratios or a shipped optimizer.

The harness runs only locally, uses generated bytes and serves the installed
browser-image-compression 2.0.2 bundle over loopback. No upstream code is copied.
The native-stream candidate only recompresses existing filtered scanlines; it does
not choose better filters, palettes or color types. The Node harness assembles
trusted fixtures and validates output with node:zlib and installed Jimp. It is
not an admission parser for untrusted files. Native canvas/Jimp comparisons are
8-bit RGBA observations; exact inflated-byte comparison additionally detects
16-bit precision/hidden-sample changes in the stream candidate.

## Reproduce

Install the lockfile dependencies and Playwright browsers, then run:

```sh
node scripts/research/png-feasibility.mjs --output /workspace/work/png-feasibility/results.json
```

Three sequential samples per candidate/fixture/browser; first result is included
(no discarded warmup). Timing is informational and has no pass/fail threshold.
Fixture generation and Node output assembly/validation are excluded. Timings
include IPC serialization/transfer and result collection. Library/canvas include
browser decode/encode; stream timings
include worker startup, decompression/compression and worker message transfer, but
not Node PNG assembly. These are different operations, not a normalized speed race.
No memory measurement or hard native allocation quota is inferred from byte caps.
Each browser operation has a 15-second parent deadline; a failure closes its browser
in finally. The stream worker additionally has a 10-second termination deadline.
Library/canvas main-thread work has no synchronous preemption guarantee.

## Measured results

Run on 2026-10-21, Node 24.19.0, Playwright's Chromium 140.0.7339.186,
Firefox 141.0 and WebKit 26.0. [Complete machine report](lossless-png-benchmark.json)
contains 81 rows / 243 measured executions, fixture hashes, individual timings,
versions and 9 budget/deadline/recovery/network controls. All passed. Fixtures are
128x96 except indexed 257x96 and Adam7 255x191. The gradient has 12288 distinct
colors; this is a deliberately small synthetic corpus, not a customer benchmark.

Native IDAT candidate sizes below precede non-inflation selection:

| Fixture | Original bytes | Chromium | Firefox | WebKit |
| --- | ---: | ---: | ---: | ---: |
| Flat, uncompressed | 49316 | 382 | 384 | 1470 |
| Same pixels, zlib9 | 349 | 382 | 384 | 1470 |
| Many-color gradient | 49316 | 39595 | 39601 | 39601 |
| Noise, zlib9 | 42211 | 42211 | 42313 | 42313 |
| Alpha and hidden RGB | 49410 | 35717 | 24624 | 24624 |
| Opaque with metadata | 49410 | 476 | 478 | 1564 |
| 16-bit low sample bits | 98478 | 28793 | 28549 | 19271 |
| 2-bit indexed | 6444 | 168 | 168 | 186 |
| Adam7 RGBA | 195267 | 152547 | 152870 | 152870 |

All 27 native-IDAT rows (81 executions) preserve every inflated scanline byte,
every non-IDAT chunk byte including CRC, dimensions and independently decoded
8-bit RGBA. Original 349-byte flat and 42211-byte noise files are retained in all
engines. CompressionStream's deflate output differs by engine; exact PNG bytes
and savings are not portable guarantees.

Maximum-quality library output changes decoded RGBA in 6/9 fixtures in every
engine: gradient, noise, alpha/hidden RGB, 16-bit, indexed and Adam7. The installed
MIT library 2.0.2 uses UPNG.encode with 4096*quality after canvas decode, not a
public unquantized PNG path. This experiment uses its public API, quality 1,
maxIteration 1 and no target-size pressure. It does not benchmark the existing
tool's default quality 50, worker/UI ownership or 1 MiB target.

Native canvas changes RGBA for alpha/hidden RGB and indexed-transparency fixtures
in every engine; metadata-bearing fixtures lose ancillary chunks. A passing
8-bit RGBA comparison for the 16-bit canvas fixture does not preserve its lower
sample bits: IHDR depth changes to 8 and filtered bytes differ. Re-encoding may
legitimately change filters/color type, so filtered-byte inequality alone is not
proof of pixel loss in an arbitrary encoder; it is the stronger preservation
invariant deliberately chosen for this IDAT-only candidate.

Native-IDAT median end-to-end harness times range 24.8-2064.2ms Chromium,
20.8-2748.1ms Firefox and 28.4-1511.6ms WebKit across these fixtures. Protocol
serialization/array transfer and host contention are included; these values do
not isolate codec CPU time, prove production responsiveness or support a speed
ranking. Run a production worker with transferable buffers and realistic fixtures
before setting UI performance expectations. No memory/large-image benchmark was
performed. Flat uncompressed inputs exaggerate savings; already optimized flat
and noise fixtures show why no fixed reduction should be promised.

## Decision and next implementation contract

Proceed with a separately scoped, dependency-free **IDAT recompression MVP** if
the product explicitly accepts best-effort reduction. Do not rename the current
palette compressor or advertise an oxipng-equivalent optimizer. Keep the lossless
milestone planned until that implementation is merged and verified.

| Option | Decision / maintenance and license impact |
| --- | --- |
| Existing browser-image-compression | Keep for its current palette tool; public path fails strict sample/metadata acceptance. MIT already installed; no new adoption. |
| Canvas PNG | Reject for strict lossless preservation of transparent samples, 16-bit samples and metadata; browser API adds no package. |
| Native streams on existing IDAT | Select for a narrow future MVP: exact scanlines/non-IDAT chunks survive and some inputs shrink. No added runtime package, binary or remote asset. Filters/color type stay unchanged, so savings are limited. |
| Dedicated WASM optimizer | Defer evaluation until a demonstrated compression need justifies binary download/startup, license/provenance, maintenance and resource review. No untested binary or license claim is adopted here. |

Owner: Orvulix maintainer. The next task must provide all of the following before
shipping; this experimental harness does not implement these runtime contracts:

- A separate feature-local strict PNG parser and CRC checks, valid header/depth/
  color combinations, consecutive IDAT, exact expected scanline expansion including
  Adam7, IEND and trailing-byte rules. Reject APNG/unknown critical chunks and
  explicitly decide handling of unknown unsafe-to-copy ancillary chunks. Preserve
  known metadata verbatim; do not silently strip profiles, gamma or EXIF.
- Admission before native preview/decode; bounded file/chunk/geometry/filtered/
  compressed/output bytes, checked before allocation and while streaming. The
  spike's 4 MiB input and 32 MiB stream budgets are not measured production limits.
  Metadata is not decompressed by the candidate, but a downstream image decoder
  may parse it; resource limits are not a general decoder security proof.
- A disposable worker with transferable buffers, hard termination on cancellation/
  deadline, current-input ownership, stale-result/error rejection, URL cleanup
  and valid recovery. Unsupported stream APIs must get actionable guidance with
  no lossy fallback. Original bytes win when candidate size is equal/larger.
- Strict parser boundary tests, malicious expansion/corruption cases, native output
  sample/chunk comparisons, cancellation/navigation races, keyboard/mobile UX,
  production metadata and Pages worker prefix/noindex validation. Benchmark the
  real built worker separately; no paid API, upload or automatic persistence.

No runtime integrations, routes, CI policy, dependencies or production settings
change in this spike. Rollback removes these research files and backlog link.

## Environment and research provenance

The cloud image lacked WebKit libraries and root access. Debian libraries were
downloaded/extracted into task scratch and linked into the local browser's sys/lib.
Playwright's host dlopen probe checks global ldconfig, which cannot see the local
GLES library; the benchmark used PLAYWRIGHT_SKIP_VALIDATE_HOST_REQUIREMENTS=1
after supplying the actual libraries and successfully launching native WebKit.
This is an environment probe limitation, not a skipped benchmark assertion or CI
gate. All three engines actually executed every row and all worker controls.
No host package, browser-library link or environment flag is shipped by this PR.
